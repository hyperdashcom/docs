자체 Hyperliquid 노드를 운영하는 팀은 시장 데이터를 피어에 의존합니다. 퍼블릭 gossip 피어는 수용 용량이 제한적이고, 사전 통보 없이 연결이 끊기며, 부하가 걸리면 성능이 저하됩니다. 네트워크 업그레이드 시점에는 특히 두드러집니다.

<Note>
  **Direct Sentry Peering은 고객사의 노드와, 당사 검증자와 동일 위치에 배치된 Hyperdash 센트리 인프라를 연결하는 화이트리스트 기반 전용 연결입니다.** 중간 계층 없이 한 홉으로 연결됩니다.
</Note>

## 대상 고객

자체 비검증 Hyperliquid 노드를 이미 운영 중이거나 운영할 준비가 되어 있고, 네트워크로 향하는 안정적인 경로를 원하는 팀을 위한 서비스입니다.

- 마켓 메이커 및 지연에 민감한 트레이딩 회사
- 퀀트 및 리서치 펀드
- 데이터 및 분석 제공업체
- Hyperliquid 위에서 개발하는 인프라 팀

## 피어링과 호스팅 피드 비교

센트리 피어링은 배포 계층 자체를 제거합니다. 호스팅 피드는 데이터가 고객사에 도달하기 전에 반드시 수신, 처리, 재전송 과정을 거칩니다. 직접 피어링에서는 고객사의 노드가 Hyperliquid 네이티브 gossip 프로토콜로 블록을 수신하고, 디코딩은 로컬에서 수행합니다.

피어링은 이미 자체 노드를 운영 중인 팀에 적합합니다. 노드를 직접 운영하고 싶지 않다면 API 접근에 대해 문의해 주십시오.

## 제공 내용

- Hyperliquid 네이티브 gossip 프로토콜을 통한 **블록 및 상태 업데이트**
- **멤풀 트랜잭션.** 당사 인프라는 `split_client_blocks`를 전 구간에서 실행하므로, 고객사 노드에 `mempool_txs`가 기록됩니다
- **화이트리스트 IP 3개** 제공. 공용 용량이 아니라 고객사 노드 전용으로 확보됩니다
- **추가 IP 및 리전**은 요청 시 제공하므로, 스테이징에서 프로덕션으로 옮길 때 재온보딩이 필요 없습니다

당사는 고객사의 체결 경로에 결코 개입하지 않습니다. 주문 제출은 Hyperliquid API로 직접 전달됩니다.

노드는 피어링하는 센트리와 동일한 리전에 배치하십시오. 홉 수가 적을수록 체결, 블록, 상태 업데이트의 테일 레이턴시가 낮아집니다. 실제 개선 폭은 고객사의 인프라, 리전, 처리 파이프라인에 따라 다르며, gossip 계층의 지연은 네트워크가 결정합니다.

## 시작하기 전에

고객사가 직접 운영하는 비검증 Hyperliquid 노드와 고정 공인 IP를 갖춘 머신이 필요합니다. 하드웨어, 운영체제, 포트 요구 사항은 당사가 아니라 Hyperliquid가 정합니다. 최신 사양은 [Hyperliquid 노드 저장소](https://github.com/hyperliquid-dex/node)를 참고하십시오.

멤풀 수집을 활성화하기 전에 디스크와 대역폭을 충분히 산정하십시오. `mempool_txs`는 지속적으로 기록되며, 블록 데이터만 받을 때보다 용량이 훨씬 큽니다.

## 설정

<Steps>
  <Step title="화이트리스트 등록">
    노드의 고정 IP를 보내 주십시오. 당사 검증자 센트리 노드에 화이트리스트로 등록하고, 해당 리전의 센트리 IP를 회신해 드립니다.
  </Step>
  <Step title="구성">
    `~/override_gossip_config.json`의 gossip 오버라이드 설정에서 당사 센트리 IP를 루트 항목으로 지정합니다.

    ```json
    {
      "root_node_ips": [{ "Ip": "<sentry-ip-we-provide>" }],
      "try_new_peers": false,
      "chain": "Mainnet"
    }
    ```

    `try_new_peers`를 `false`로 설정하면 노드가 퍼블릭 피어로 되돌아가지 않고 확보된 피어에 계속 연결됩니다.
  </Step>
  <Step title="활성화">
    노드를 재시작하고 블록이 정상적으로 적용되는지 확인하십시오. 이제 빠르고 안정적인 상시 연결이 가동됩니다.
  </Step>
</Steps>
